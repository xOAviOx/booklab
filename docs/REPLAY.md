# Replay model

## Recording

- Capture `BTC/USD` on Kraken Spot WebSocket v2 at `wss://ws.kraken.com/v2`. Subscribe to `book` with `depth: 25` per side and `snapshot: true`. Start the recording at the first verified snapshot. Ignore subscription acknowledgments and heartbeats as book events. [WebSocket endpoints](https://docs.kraken.com/exchange/guides/websockets/introduction) · [Level 2 book channel](https://docs.kraken.com/exchange/api-reference/spot-websocket-v2/book)
- Store a UTF-8 NDJSON file. Line one has `version` (`1`), `source` (`synthetic` or `kraken`), `symbol` (`BTC/USD`), and `depth` (`25`). Each following line contains `elapsed_us`, a nonnegative JSON safe integer, and `frame`, the original Kraken-shaped `book` message as a JSON string. The first event is a snapshot at `elapsed_us: 0`. Use the same format and validator for the demo, import, and capture.
- Stamp incoming messages on entry to the worker’s WebSocket handler using elapsed monotonic time from `performance.now()`. Compute integer microseconds relative to the first accepted snapshot. File order is the tie-breaker when events share a time. Keep any Kraken timestamps in the original payload for inspection. Comparison times use the recorded receive clock, which includes network and browser scheduling effects. [Performance.now](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)
- One version-1 recording contains one continuous segment. Cap live capture at 60 seconds or 10 MiB of encoded recording data, whichever comes first. On a disconnect or validation failure, stop and retain the valid prefix through the last verified frame. A fresh capture starts from a fresh snapshot. Reject imports with invalid structure, unsupported headers, descending times, missing initial snapshots, unexpected later snapshots, or failed validation as a whole. Check the file size against the same 10 MiB limit before reading.

## Reconstruct the book

1. Preserve the price and quantity lexemes from the raw frame, including trailing zeros. Accept plain decimal JSON tokens and equivalent quoted decimals. Rust can extract numeric tokens with `serde_json::value::RawValue`. Keep exact decimal strings for CRC and convert a separate representation for numeric ordering and arithmetic. [Serde RawValue](https://docs.rs/serde_json/latest/serde_json/value/struct.RawValue.html)
2. Load the initial snapshot with its bids and asks. Apply each update in message order, including repeated updates to one price within a message. A positive quantity replaces that level’s size and updates its checksum tokens. Zero deletes the level. Apply the whole message before pruning both sides to the subscribed depth.
3. Check every snapshot and update. For the ten best asks in ascending order, then the ten best bids in descending order, append each level’s price digits then quantity digits after removing decimal points and leading zeros. Keep trailing zeros. Compare the unsigned CRC32 of the concatenation with the frame checksum. The checksum covers the top ten per side even when the replay displays or consumes deeper levels. [Kraken v2 checksum guide](https://docs.kraken.com/exchange/guides/websockets/book-checksum-v2)
4. Publish a rebuilt state only after all validation succeeds. Discard invalid mutations. Treat malformed frames, unexpected symbols, or crossed books after a complete update as integrity failures. A missing side can be valid and contributes zero liquidity on that side.

## Seek and simulate

- A query takes the playhead time, delay, side, and a positive BTC amount. Pass the playhead and delay to Rust as nonnegative integer microseconds. Convert the UI’s delay from milliseconds to microseconds at the worker boundary. Use checked addition for the delayed time. At each time, use the state after every complete frame with `elapsed_us` at or before that time. Between frames the last verified book holds. The valid domain is inclusive from the snapshot through the last verified book frame. An out-of-range time is unavailable.
- Compare the same order independently against both books. A buy consumes asks from lowest to highest price. A sell consumes bids from highest to lowest. At each level, take the smaller of the displayed quantity and the order’s remainder. Stop when filled or when the recorded side is exhausted. The replay never carries simulated consumption into the next frame or the other scenario.
- Return consumed levels, filled and unfilled BTC, USD notional, and volume-weighted average price in USD per BTC. Average price is total filled notional divided by filled quantity. The signed delta is delayed average minus baseline average. Return it only when both scenarios fill some BTC. Compare the unrounded averages before formatting.
- Represent normalized price and quantity as fixed-point integers with up to eight decimal places each for this BTC/USD model. Accept values that fit exactly, including extra trailing zeros in feed tokens. Use checked integer arithmetic for notional and exact ratio calculations. Round average prices and the delta to the nearest cent for presentation only, with halfway values rounded away from zero. Keep the exact sign of the delta and display changes that round to zero as under one cent with their direction. Reject unsupported precision, overflow, or invalid order size with a clear error.

## Golden examples

- Use Kraken’s published snapshot and expected CRC32 `3310070434` as an independent checksum fixture. Add a sequence where repeated updates and a deletion occur in one frame and a level falls outside the subscribed depth. [Kraken checksum example](https://docs.kraken.com/exchange/guides/websockets/book-checksum-v2#example)
- In the bundled demo, pause at `4.000 s` with a `250 ms` delay and a buy of `0.75 BTC`. At the playhead, consume `0.25 BTC @ $100,000` and `0.50 BTC @ $100,002`. At `4.250 s`, consume `0.25 BTC @ $100,004` and `0.50 BTC @ $100,006`. Both fill completely. The averages round to `$100,001.33` and `$100,005.33` with a delta of `+$4.00 per BTC`. Keep enough additional bids and asks in the fixture to exercise checksum ordering.
